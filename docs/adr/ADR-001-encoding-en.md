# ADR-001: UTF-8 encoding without BOM

## Status

Accepted.

## Date

2026-11-09.

## Author

Viki P. Sitzer (@mvikips). Roles in docs/conventions/attribution.md.

## Context

The 30kT repository contains Markdown, JSON, YAML, PowerShell and Python files. Over the first milestones, three encoding incidents were recorded:

- m11 (A02): a BOM was detected at the beginning of a notes file, breaking parsers that assume UTF-8 without BOM.
- R3 (A06): PowerShell 5.1 corrupts non-ASCII arguments when passing them to native executables. The title of issue #2 changed from Inspeccion with accent to Inspeccion without accent, losing the original byte (C3 B3 to 3F).
- Incident #2: rewriting a title with accents replaced the accented vowel with an ASCII question mark.

All three incidents share one cause: the absence of an explicit encoding policy. The absence forces every tool to infer, and inferences are not consistent.

## Decision

Every file in the repository is saved with UTF-8 encoding without BOM. Plain text, Markdown, JSON, YAML, SQL, scripts and source code files follow the same rule.

Operational clarifications:

- Files created or edited with a text editor are saved in UTF-8 without BOM. VSCode does this by default.
- Files generated by script use explicit UTF-8 without BOM encoding.
- JSON files consumed by GitHub Actions must not have BOM. Actions parsers reject or mishandle BOM.
- Commit messages, issue titles and PR titles are written in ASCII. If a title requires accents, it is edited via API with a UTF-8 without BOM JSON file, avoiding the PowerShell 5.1 command line.

## Consequences

Positive:

- Eliminates the class of incidents documented in Context.
- Ensures compatibility with tools that assume UTF-8 without BOM: YAML parsers, Actions, git diff, gh CLI.
- Simplifies review: files with BOM generate spurious diffs.

Negative:

- Requires discipline on every new file. The rule does not self-verify.
- Collaborators using default Windows tools (old Notepad, certain Excel versions) may reintroduce BOM.

Mitigation:

- Add automatic BOM verification to the CI workflow (A07, #8).
- Document the procedure in docs/conventions/language.md.

## Discarded alternatives

- UTF-8 with BOM: incompatible with Actions parsers and several command-line tools. BOM adds no information in UTF-8.
- Latin-1 or ISO-8859-1: covers fewer characters than UTF-8. Incompatible with the trilingual documentation adopted in ADR-002.
- UTF-16: consumes twice the space, incompatible with most Unix tools, no advantage for this case.
